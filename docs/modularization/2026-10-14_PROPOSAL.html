00Summary

Do not split webphone into multiple go.mod modules. This is the third consecutive assessment to reach that verdict (2026-09-19, 2026-09-30, today), and today’s evidence is the strongest yet: a GitHub code search plus a local-tree grep confirm that nothing anywhere imports github.com/larsartmann/webphone/... as a Go module. Every benefit a module boundary could pay out (compile-time fences, independent versioning, consumer-scoped imports) requires a consumer. There are none. The one deliverable is a single binary that the consuming stack rides via Nix pins.

Meanwhile the cost side is not hypothetical in this repo: the vendorHash red-main incidents of 10-06 and 10-09 came from plain dependency bumps, and a split multiplies exactly that fragility class. The compile-time-boundary benefit the split would buy is already realized at package granularity and enforced by internal/arch tests that run in every gate.

The bottom line Keep the single module. The named revisit trigger stands: a second Go consumer importing internal/domain or internal/gateway reopens this question. The refinement that IS worth doing operates below module level: the internal/server carve, already TRIGGERED in TODO_LIST.md as its own train.

02Today’s evidence

Four facts, each re-verified against the tree today.

Decisive

Zero external Go consumers

gh search code larsartmann/webphone + local grep across ~/projects

The only references outside this repo are the consuming stack’s README and go-health’s fleet-repos list, neither of which imports a Go package. The composability test every proposed boundary must pass (“does it let consumers import only what they need?”) has no consumers to serve. With one consumer (the binary) needing everything, every seam earns nothing.

Structural blocker · FM#6

Every package lives under internal/

all 23 packages, by design

A sub-module’s internal/ tree is invisible to every other module. Any go.mod split therefore forces one of two strictly worse outcomes: move packages out of internal/, publishing app internals as public API against the app’s own design, or duplicate shared types across modules (split brain, a declared defect class in this repo). This alone disqualifies the split regardless of the other evidence.

Benefit already realized

The module DAG already exists at package granularity

internal/arch/arch_test.go, green at assessment time

The package graph is the exact DAG a module split would draw: domain is the zero-internal-dependency core; seven leaves (asr, blob, crm, pbx, sipcred, textagent, vcard) import nothing internal; services form the mid layer; server and the app composition root sit on top. The arch test suite enforces domain purity, services-never-import-server/web, and DI staying inside the composition root, failing every gate rather than just review.

Corroborating

Co-change validates the package boundaries

git log, last 150 commits

Only 3 of 150 commits (2%) touch five or more packages. Churn concentrates where the product work is: server (59 file-events) and web/views (26), while domain (6) and the leaves are nearly stable. The “all packages change together” failure signal is absent; the existing boundaries already match the change patterns.

03Split candidates, evaluated and dismissed

Direction neutrality demands the split case gets its day in court. Each candidate seam, scored against the two questions that replace “merge or split?”: right decomposition depth, and composability payoff.

Candidate module Would own Composability payoff Verdict
domain Core types, branded ids Zero consumers today Keep as package
config Env + JSON loading Consumed only by app/gateway/server Keep as package
store + blob SQLite persistence, blobs Internal to the one binary Keep as packages
gateway Loopback/webhook seam pbx-artmann consumes it over HTTP, not via Go imports Keep as package
sipcred Credential derivation (74 LOC) FreeSWITCH validates via webphone’s directory endpoint; no second deriver exists Keep as package
Why the cost side wins by default Each new module means its own go.mod + vendor tree or a workspace vendor decision, a vendorHash re-pin ritual per bump, whole-tree narHash churn for the stack and pbx-artmann pins, and re-validation of BuildFlow gates, release.sh, smoke, and flake checks. The vendorHash red-main incidents (10-06, 10-09) show this fragility is real here. A boundary needs a payoff to justify that; zero consumers means zero payoff.

04Re-trigger criteria (falsifiable)

This verdict is durable but not permanent. Re-run the modularize workflow when any of these becomes true:

1
A second Go consumer appears Any repository importing internal/domain or internal/gateway as a module. This is the trigger named by the 09-30 review; it remains the primary one.
2
The stack switches from Nix pins to Go imports If nix-international-telephony or pbx-artmann begin importing webphone packages directly, versioned boundaries start earning version-ceremony money.
3
A sub-domain grows its own release cadence E.g. the island or the gateway becoming a separately deployed artifact would justify a module boundary at that seam, not before.

05What IS worth doing instead

The 09-30 review already located the refinement that captures module-level benefits at package-move cost, and today’s data confirms its trigger fired: internal/server has grown from 19 to 26 source files since the trigger was set.

One home per fact The server carve (split server/api JSON endpoints and server/hooks webhook ingest out of the wiring core) is TRIGGERED and dependency-mapped in TODO_LIST.md, deliberately scheduled as its own train. This report does not duplicate that item; it ratifies that the carve, not a go.mod split, is the right tool for the coupling concern.
