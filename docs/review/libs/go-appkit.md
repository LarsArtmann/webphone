## The open-mind pass: what WOULD make the framework reconsiderable

The owner's hypothesis — "maybe appkit needs changes first" — taken seriously, the changes are nameable:

1. **Per-surface health grading** — two readiness gradings of overlapping check sets (strict all-legs /healthz beside a lenient dashboard view), or composition with an external readiness handler such as cqrs-htmx's. **FILED 2026-11-12: go-appkit#59.**
2. **An aggregates-only metrics mode** — no `route`/`method` labels; webphone's /metrics leak test pins that privacy line. **FILED 2026-11-12: go-appkit#60.**
3. **First-class CSP exception lanes** — per-subtree header overrides (nonce lane at /login, `unsafe-eval` at /health) as config, not middleware surgery.
4. ~~**Consumer-owned drain ordering**~~ — **WITHDRAWN 2026-11-12 (fleet-frame re-check)**: appkit's `DrainHooks` fire at drain start while traffic is still served (exactly the `ExtensionHubs.Shutdown` stream release) and `ShutdownHooks` run after connections release (the trace seam's last drain). The residue is only the outside-the-injector stance and the 5-part bootreport contract — opinions, not walls.
5. (httpx) **Success-status override** — the error side is already expressive (an error's own `HTTPStatuser` wins over the family table, go-error-family v0.12.0); the 202-lane gap is the success path. **FILED 2026-11-12: go-appkit#61.**
6. (config) **`__`-nested env binding, unknown-key warn mode, map sections** — appkit would have to reverse its own koanf verdict; a charter reversal, not an extension. Treat as permanent.

The owner's fleet constraint (2026-11-12) reframes this list: these are not waiting conditions — the owner owns BOTH repos, so 1–3 and 5 are upstream asks webphone files and benefits from fleet-wide (per-surface health grading and a label-free metrics mode are good for every app, not just this one). The collective-improvement lanes are three: (a) the shared-library substrate webphone already rides (fixes in httputil/go-health/go-error-family/go-cqrs-lite propagate to all 41 fleet apps today); (b) EXTRACTING webphone's best recipes upstream — the walls above ARE the extraction backlog, and appkit's own battery-swap recipes target the simpler apps first (dnsblockd −~1.6k LOC, ChastityAPI −~4.8k); (c) webphone migrating LAST, once its walls exist upstream. What is NOT rational for a time-constrained owner: adopting the framework now and bypassing it at every wall — that pays the dependency + version-sync + indirection cost AND keeps the hand-rolled code, the worst of both worlds.

Honest summary: appkit is a good library getting better — v0.12.0 riding the same `httputil.Server` seam webphone chose is convergence evidence — whose product (wiring defaults) is currently narrower than webphone's opinions. This re-review changes the report's SHAPE (one module promoted from nothing to candidate; the stale "every module re-wraps" claim retired; one wall withdrawn), not the framework verdict — but the verdict's TRAJECTORY is convergence, and the todo is on webphone's side of the fence: file the walls upstream.

## Ruling

Framework layer (core, preset, and the re-wrappers): **NO-GO stands**, re-ruled 2026-11-12 against v0.12.0 + the 13-module inventory. The 2026-10-23 "every module re-wraps what webphone composes directly" claim is RETIRED — stale for httpx, config, and flightrecorderhealth — and replaced by the per-module expressiveness evidence above. `flightrecorderhealth`: the refresh trigger legitimately fired; first module-level adoption candidate, demand-gated row in TODO_LIST.

**Refresh trigger:** an appkit tag beyond v0.12.0 shipping a NEW battery (sweep the module table above — the 2026-11-12 pass proved the inventory drifts in days, not quarters); the flightrecorderhealth row's own demand trigger; a `Type=notify` conversion (shared with go-daemon); a second service wanting webphone's exact HTTP-shell recipe (then the RECIPE-extraction question — appkit/preset vs httputil — not an adoption).
