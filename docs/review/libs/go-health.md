## What the library offers

`New(injector, opts...)` — discovers checks via `do.HealthcheckerWithContext` implementations in a samber/do container; `NewChecks(map[string]CheckFunc)` for explicit compositions; `Probe` lifecycle (`Start` refresh loop, `Shutdown`, `MarkShuttingDown`); critical vs non-critical roll-up (`WithCriticalServices` — critical failures fail readiness; others visible but non-gating); handlers `LivenessHandler`/`ReadinessHandler`/`StartupHandler`/`Healthz`/`RegisterRoutes`; evaluation/caching (`Evaluate`, `CachedResponse*` — the dashboard consumes these internally); options (timeouts, refresh, instance ID, version, boot time, evaluation hooks, recorders); sub-packages `aggregate`, `federation`, `checks` (disk/memory batteries).

## How webphone uses it

- **Injector discovery**: `health.New(injector, health.WithCriticalServices("sqlite","blob-dir"), health.WithRefreshInterval(probeRefreshIf(cfg.Dashboard.Enable)))` (internal/app/app.go:403-406) — the container's services implement `do.HealthcheckerWithContext` and are discovered; refresh 1s only while the dashboard is on.
- **Critical pair** `sqlite` + `blob-dir` roll up to readiness; userauth/asr/crm legs are non-critical (visible, non-gating) — the split pinned from the readiness side by `TestCRMLegGatesReadinessDeliberately` (internal/app/health_crm_test.go:39): `/healthz` grades the CRM leg strictly while the go-health probe WARNs — same fact, two readings, both intended.
- **Lifecycle**: `Probe.Start(ctx)` / `Probe.Shutdown()` ride App.Start/App.Shutdown (app.go:700,755); the probe is deliberately NOT registered in its own injector (self-recursion guard, app.go:105-112) and is threaded to server.Deps + dashboard, never registered in the injector it reads.
- **`/livez` + `/startupz`** from the same probe instance (server.go:841-842, `LivenessHandler`/`StartupHandler`; `health.NewChecks` fallback for test compositions at server.go:838-840, carrying the same `WithCriticalServices` pair).
- **`/healthz` is deliberately NOT go-health**: it is `cqrshtmx.ReadinessHandler(cqrshtmx.NamedCheck{...})` with per-check timeouts (server.go:741-792) — one readiness truth, split documented in AGENTS.md.

## Ruling

**LANDED 2026-11-04:** bumped to v0.9.0 together with go-health-dashboard v0.13.0 (the wave's coordinated consumer side — see the header note). No webphone-side sanitizer wiring exists or is needed: the library applies `CoerceValidUTF8` at its own serialization seam before marshaling, and webphone never marshals a `health.Response` itself. The dashboard half required finishing the wave's stalled release (the v0.13.0 release commit was pushed untagged): verified green in a detached worktree, tagged, proxy-verified, then bumped. Everything else is at its deliberate boundary.

**2026-11-22 re-verify:** currency holds — pin v0.10.0 = upstream latest (local tag v0.10.0; master's `[Unreleased]` is empty scaffolding — nothing staged, no consumed-surface intent to read). Wiring re-derived after the live-refactor churn: `/livez`+`/startupz` still one probe (server.go:841-842), `CoerceValidUTF8` still needs zero webphone wiring (rg over webphone Go sources → 0 hits; the coercion remains inside the library's serialization seam and webphone marshals no `health.Response` itself), the per-surface criticality split still pinned (health_crm_test.go + the NewChecks fallback carrying the same critical pair), and `WithVersion`/`RegisterRoutes`/`DefaultRoutes` remain unconsumed — which is why v0.10.0's breaking Routes changes landed here with build and suite untouched. One correction recorded above: this report's earlier "v0.9.0→v0.10.0 = no API change" gloss was wrong (the changelog's v0.10.0 is the Routes release); the error was characterization-only — no score row touches the changed surface. Adoption stays 100/100; no verdict movement.

**Refresh trigger:** a second readiness consumer; a multi-instance deployment; the go-health-dashboard gaining a surface that needs `WithEvaluationHook`.
