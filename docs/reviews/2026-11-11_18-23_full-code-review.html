03Verified findings still open

High

Hold/resume settles on send, not on the re-INVITE verdict

internal/web/assets/island/app/calls.js:135-165 (verified by lead)

await entry.session.invite() resolves when the re-INVITE is SENT; the settled entry.held state is committed without network confirmation, violating the island honesty contract for the one state machine that most needs it. The sip.js-0.21-verified fix shape: pass a requestDelegate with onAccept/onReject and await a promise those callbacks resolve. This is a focused rework of load-bearing call code — deliberately NOT rushed in this review; it needs its own train with call-transitions pins updated.

Medium

/hooks/ring fans out synchronously on the request context

internal/server/hooks/ring.go:50-79 (verified by lead)

The wire contract says the dialplan’s 202 is inert and “the dialplan must never depend on push health”, but the fan-out sends sequentially on the hook request’s context: a dead transport delays the ack by up to targets × client timeout (~10s each, 8 devices worst case). Fix shape: the notifyDraftReady pattern (context.WithoutCancel + budget, detached goroutine) — ring_test’s prune pins need a synchronization point. Own train.

Medium · needs probe

Concurrent first-sight may split a thread (unverified data-loss claim)

internal/cqrs/threads.go:104 + internal/messaging/service.go:133,:204

The sweep claimed a dropped-message wedge via the cqrs.thread_identity rejection; the lead could not reproduce that exact path from source. What the code DOES suggest: two concurrent first-sights for the same (owner, remote) race FindThread’s projection visibility (D7 lag) and may mint two threads for one remote — a thread split, not a reject. Needs a focused race probe before any fix; the webhook lane may already serialize.
