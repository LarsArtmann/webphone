Line ownership: how phone numbers connect to users

The sixth data-model review, scoped to one question the owner named: "we connect phone numbers to users very stupidly." The review found the missing concept (the Line), redesigned the model around it, and the same train SHIPPED it — model, wire, and UI.

00Summary

The platform's central concept — a phone LINE (an extension plus the number it presents) — did not exist as a type. Ownership was three parallel string maps joined ad hoc at every consumer, the wire carried two uncorrelated lists, the line switcher showed bare PBX codes, and Settings had no surface that answered "which numbers are mine." Twelve visible symptoms, one root cause.

The bottom line Shipped. authmap.Line is now the one owned-identity type; the composition root joins the operator's three feeds exactly once; the wire carries a typed lines array; the switcher, whoami, Settings ("My account") and the Admin inventory render numbers, not codes. SSO-only deployments resolve their identity too — a latent gap the redesign surfaced and closed.

◆What was already right

The redesign builds on rails earlier reviews laid: the join landed in ONE place because the composition-root doctrine already existed.

+
authmap was already the one mapping home The 2026-10-28 doctrine ("both login modes resolve through one implementation") meant adding the Line type extended an existing seam instead of founding a second one.
+
domain.Extension was already branded ParseExtension/MustParseExtension made the join type-carrying for free; no string-typed extension entered the model during the migration.
+
The Android wire tests pin behavior, not shape The JVM suite pins the credential arms only, so the numbers/extensions→lines wire change broke no consumer while keeping the contract honest.

01Problem catalog

Seven findings, one root cause each traces back to. All seven shipped fixed in this train.

Critical · P1/P4 missing entity

No Line type — the concept the product sells

config.go / authmap.go / admin.go · three maps keyed by raw strings, joined ad hoc

Ownership lived in auth.users (email→extensions), identities (extension→DID) and extension_password_files (extension→file). The platform's owned unit — a line — was the implicit intersection of three string keys, reconstructed at every consumer. 

// before: the line was whatever these three agree on
Users map[string]PasskeyUser      // email -> []extension
Identities map[string]string      // extension -> DID
ExtensionPasswordFiles map[string]string
Fix: shipped authmap.Line{Extension, DID} owned by authmap.User.Lines; the join happens once in app.mappedUsers and every consumer reads the typed model.
Critical · P5 uncorrelatable wire

The session wire carried two parallel lists

server/auth/session_identity.go · numbers[] + extensions[]

numbers was DEDUPED and DID-less extensions were DROPPED, so index i of one list did not map to index i of the other. The switcher could not label an option with its number even if it wanted to — the shape made the product's best UX inexpressible.

Fix: shipped One typed array — lines: [{extension, did}] — the active line identified by equality with the top-level extension. OpenAPI golden + Android fixtures regenerated.
Important · P9 duplicated joins

The same join written four times

app.go (three adapter loops) + admin.Numbers + numbersFor

PasskeyRuntime, SSOConfig and AdminService each parsed the same config mapping independently; two more joins lived in the admin inventory and the whoami builder. Five sites could disagree about who owns what.

Fix: shipped One helper (app.mappedUsers) feeds all three adapters; admin and whoami read the model.
Important · latent gap closed

SSO-only deployments resolved no identity

server/auth/session_identity.go · UserAuth-only resolution

Whoami resolved identity through the passkey service only; with SSO configured and passkey off, a mapped login showed a bare extension. The redesign's one resolution home (MappedIdentityWith) covers both authmaps.

Important · unenforced invariants

Line-less users and duplicate lines were representable

authmap.New · now two new codes

A mapped user with zero extensions, or one naming the same extension twice (the switcher dedups nothing), compiled fine and failed at login time.

Fix: shipped authmap.user.lines and authmap.user.duplicate_line rejections at Map construction; registry regenerated in the same commit.
UX · the "stupid" feeling, made precise

A phone product that spoke in PBX codes

island session.js / ui.js / Settings

The line switcher listed "1001, 1002". The whoami line flattened every owned number into one comma join. Settings had no account surface at all — the one place that should answer "which numbers are mine" did not exist.

Fix: shipped Switcher options read "DID · extension"; whoami leads with the ACTIVE line's number; Settings renders a "My account" group with every owned line and the active mark; Admin user rows carry the same labeled chips.
Considered · deliberately kept

The operator's three-map config shape stays

config.go / NixOS module / stack assertions

A cohesive auth.users[email].lines[] config shape was designed and declined: it would compete with identities + password files as a second home for the same facts ("declare the mapping ONCE" is a standing rejection), and the typed NixOS lane asserts the current shape. The MODEL joined them; the operator interface is unchanged — one config edit still changes ownership.

02The model that shipped

Three concepts, three invariants, one join. This is the current tree, not a proposal. 

// internal/authmap — the ONE ownership model
type Line struct {
    Extension domain.Extension // branded; ParseExtension mints
    DID       string           // verbatim owner formatting; "" = undeclared
}
func (l Line) Display() string // DID when declared, else extension:
                                // the ONE fallback rule, server + island

type User struct {
    Email       string
    DisplayName string
    Lines       []Line // >= 1 by construction; Lines[0] = session default
    Admin       bool   // identity property, resolved per request
}
func (u User) SessionLine() Line
func (u User) Has(domain.Extension) bool

// the join happens ONCE (internal/app):
func mappedUsers(users map[string]config.PasskeyUser,
                 identities map[string]string) map[string]authmap.User

// the wire (server/auth): one typed array, active by equality
type SessionLine struct {
    Extension string `json:"extension"`
    DID       string `json:"did,omitempty"`
}
Why this state is better Ownership disagreements are now compile errors (a second join cannot type-check into existence); the switcher's best possible UX became the cheap one; and every surface answers "whose number is this" from one place.
