00Summary

webphone's cqrs-htmx adoption grew from one module to five since the last audit, and the new identity lane is wired with unusual care: the usermgmt session is deliberately discarded so the webphone session stays the single truth, enrollment is token-gated through the service-level API, and the login page rides the library's templ-components build under a nonce-CSP exception. The root-library posture pinned in round 2 — middleware chain, embedded HTMX bundle, per-extension SSE hubs, honest readiness — is unchanged and still correct.

The distance to “to the max” is now concrete: one capability shipped in the versions webphone already pins (the projection readiness check), one coordinated version train (clone-detection + durable auth audit, usermgmt v4.15/v4.16 + identity-model v4.14 + webauthn v4.13), and one two-line lifecycle fix (closing the SSE hubs on shutdown).

The bottom line The single highest-leverage action needs no version bump: cqrshtmx.ProjectionReadinessCheck(svc) exists in the pinned root v4.14.1 and *usermgmt.Service implements ProjectionStatuses() in the pinned usermgmt v4.14.3 — webphone's /healthz userauth leg pings the database but never asks the projections, so a failed user-read-model leaves health green while passkey logins degrade.

Missed Opportunity · available in the pinned versions

Projection readiness check unwired — /healthz can lie while passkey logins degrade

internal/userauth/userauth.go:146-148 · internal/app/app.go:253-256 · library: projection_readiness.go (root v4.14.1, pinned), es_projection_health.go (usermgmt v4.14.3, pinned)

usermgmt's NewService runs its read models and the casbin projection on an async projectionhost (es_setup.go: projectionHost *projectionhost.Host, with an OnProjectionFailed hook webphone never sets). webphone's userauth health leg only pings the database: HealthCheck → s.db.PingContext(ctx) — the comment claims “the service's failure mode IS the database”, but a failed or backoff worker leaves the user read model stale with health still green. The library ships the exact one-liner for this, and webphone's pins already contain it: root v4.14.1 exports ProjectionReadinessCheck(provider) NamedCheck and ProjectionDrainReady, and usermgmt v4.14.3's *Service implements ProjectionStatuses() satisfying the provider interface. 

// Before (internal/server/server.go, userauth leg):
checks = append(checks, named("userauth", auth.HealthCheck)) // db ping only

// After — no version bump, the pins already carry it:
checks = append(checks, cqrshtmx.ProjectionReadinessCheck(auth.Usermgmt()))

// And at boot (userauth.New), make failures loud:
usermgmt.ServiceConfig{
        ...
        OnProjectionFailed: func(name, lastErr string) {
                log.Error("usermgmt projection failed", "projection", name, "error", lastErr)
        },
}
Recommendation Add ProjectionReadinessCheck as a second named check on the userauth leg (503 names the failing projection) and set OnProjectionFailed to a loud WARN so the log explains what health is reporting. Zero new dependencies; the health bridge module is not needed for this.
Missed Opportunity · version lag (security)

WebAuthn clone detection is dead — the identity train is two minors behind

go.mod pins: usermgmt v4.14.3, identity-model v4.12.3, webauthn v4.12.1 · latest: v4.16.0, v4.14.0, v4.13.0 · seam: internal/userauth/userauth.go:186-198

usermgmt v4.15.0 shipped WebAuthn sign-counter persistence: every successful login records the assertion's signature counter and UP/UV/backup flags (RecordCredentialUse → CredentialUsed), and a regressed counter is rejected as a conflict — WebAuthn L3 §7.2 clone detection. Without it (webphone's v4.14.3), “clone detection compared every assertion to the registration-time counter and never fired” (identity-model CHANGELOG v4.14.0). For a phone system whose passkeys mint SIP credentials, a cloned authenticator signal is a security-relevant gap. The stored flags also stop being fabricated true on reload, so go-webauthn's UV latch works as designed.

Missed Opportunity · rides the same train

Durable auth-audit journal unbumped — and one documented non-adoption reason is now stale

AGENTS.md (AuditLog projection “unwired” reasons) · library: usermgmt/auth_audit.go (v4.15.0+) · webphone's own authAudit lines

usermgmt v4.15.0 added the auth audit journal (cqrs-htmx#23): successful and failed logins and registration-closed probes become durable journal events on dedicated Auth-typed streams (best-effort append, never failing a login; unknown-user failures deliberately excluded to deny an unbounded journal-write vector). webphone's AGENTS.md records the AuditLog projection as unwired for three reasons — memory-only, no login events, unbounded. The second reason is now false at v4.15+: login_succeeded, login_failed, and registration_closed are first-class. The other two still hold for the read-side projection (audit_log.go remains an append-only in-memory slice), so webphone's hand-rolled greppable authAudit lines stay the right operational surface — but the bump makes the durable “who logged in, when” record exist in usermgmt.db, queryable long after log lines rotate.

Recommendation Fold this into finding 2's train (no extra work — the journal is automatic inside the service). Afterwards, update the AGENTS.md non-adoption note: “memory-only, unbounded projection” stays; “no login events” is retired. Reconsider surfacing only if the projection gains a bound.
Partially Used · small but real

SSE hubs are never closed — shutdown always burns the drain budget

internal/server/sse.go:34-141 (no Close anywhere) · internal/app/app.go:303 (hubs provided, no shutdown hook) · cmd/webphone/main.go:173-176 (“30s shutdown budget covers the SSE hub drain”)

The library's documented broadcaster lifecycle is defer broadcaster.Close() — closing signals every subscriber's stream to end cleanly. webphone's ExtensionHubs has no Close method; the hub map is provided into the injector without a shutdown hook, and App.Shutdown drains HTTP → probe → container without touching it. With any signed-in tab connected, the HTTP drain waits on live SSE streams until the full 30 s budget expires — every restart pays it. The comment in main.go assumes a drain mechanism that was never wired. 

// ExtensionHubs gains the lifecycle the library intends:
func (h *ExtensionHubs) Shutdown() error {
        h.mu.Lock()
        defer h.mu.Unlock()
        for key, hub := range h.hubs {
                hub.Close() //nolint:errcheck // best-effort drain
                delete(h.hubs, key)
                delete(h.seen, key)
        }
        return nil
}
// The do-injector then drains it with the other ShutdownerWithError
// services — subscribers see a clean stream end inside milliseconds.
Recommendation Implement Shutdown on ExtensionHubs (it then rides the container's existing shutdown order, asserted adapter-side in app.go). Restart time drops from “always 30 s with a tab open” to near-instant.
