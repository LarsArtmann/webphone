go-appkit: are we using it superbly?

No. We are not using it at all. This report works out whether that is a gap or a correct choice, module by module, and what one module in it (errorpages) would have bought us that our own 404 now buys instead.

Version: not a dependency Adoption score: 77 / 100 Band: high

Summary

github.com/larsartmann/go-appkit is a production HTTP service framework that composes httputil, charmbracelet/log, and go-error-family into one lifecycle. webphone imports none of it: a search of go.mod, every .nix file, and every .go file returns nothing. The only prior record is the 2026-09-24 stack deep dive, which noted “zero usage” as an observation, not as a verdict.

The interesting part is that webphone already does, by hand, almost everything appkit assembles. The duplicate is not a gap; it is a second implementation of the same composition, built from the same underlying libraries (httputil, go-health, go-health-dashboard, go-sse, go-cqrs-lite/metaengine). Adopting appkit now would wrap the wrappers. Two modules remain genuinely unadopted, and one of those is rejected on purpose in our own NixOS module.

What webphone already does well

Composition without a framework

The middleware order is explicit and tested (internal/server/server.go:525): enrichment, request logging, server timing, security headers, recovery. appkit's default stack is the same list; owning it locally is why ServerTimingMiddlewareWhen can be env-gated and why the user extractor can be deliberately nil.

Health that answers the honest question

go-health is used directly in internal/app/app.go:293 with critical services, a startup latch, and a 1s refresh only while the dashboard is on. appkit/health exists to wire exactly this; we already have it, plus the composition-root lifecycle around it.

Findings

Partially used: metrics depth

Library offers: request histograms, response totals, in-flight and build-info gauges behind MetricsConfig. We do: internal/server/metrics.go:20 exposes aggregates-only counters plus build facts. That is a deliberate privacy line (never per-extension data), but latency percentiles are aggregates too and would answer “is the PBX slow or is the browser slow”. Impact: medium for operators, low for users. Effort: small.

Partially used: classified error contracts

Library offers: errorpages.Write, the JSON shape {family, code, message, title, why, fix, context}, and pretty 405s via errorpages.Wrap. We do: HTML 404 is now our own shell-integrated page (internal/web/views/error.templ, NotFoundPanel), while the JSON lanes answer ad-hoc bodies per handler. Ruling: decline the HTML half (a standalone minimal page would drop the session/CSRF shell, the i18n negotiation and the island), keep the JSON-contract idea as an open, unscheduled candidate.

Partially used: generated API docs

Library offers: OpenAPI/AsyncAPI/D2 generation from Go types. We do: a hand-written /openapi.json. Keeping it hand-written avoids codegen in the build and keeps the served bytes reviewable in a diff. Revisit only if the API surface grows past a page or two.

Missed opportunity: flight recorder

Library offers: on-demand runtime/trace capture triggered by an error threshold or an endpoint, built on go-flightrecorder which is already an indirect dependency of this build. We do: nothing. A wedged SIP reconnect or a lock convoy currently means reproducing on a dev box. Impact: high for the one bad incident per quarter. Effort: one middleware plus one endpoint, gated off by default.

Not applicable, with reasons

  • systemd (sd_notify): rejected on purpose. Our unit is Type=simple by decision (package/nixos-module.nix:91: readiness is the /startupz latch, not sd_notify; do not add Type=notify or watchdog restarts).
  • otel: one binary on one host, no collector; request ids, slog correlation and /metrics cover the need.
  • cqrs: no event-sourced domain state. The ratified position (AGENTS.md, single go.mod) stands; metaengine read models are the only CQRS-adjacent surface, and they are already direct.

Verdict

Do not adopt go-appkit. The framework layer would replace a composition root we control, with no capability gain: every module either re-wraps a library we already use directly, is deliberately rejected (systemd), or does not apply (otel, cqrs). The one live opportunity is the flight recorder, which can be taken directly from go-flightrecorder without the framework.
