00Summary

The direct answer to "do we use catalog superbly?" is no — webphone does not use it at all. Not in go.mod, not in a single import. On one path that non-use is a recorded owner ruling with sound reasoning; on the two remaining applicable paths it is an unexamined gap in which webphone hand-maintains exactly the artifacts the library generates from Go types.

The bottom line The EventCatalog path is ruled out by an owner decision (2026-10-19: no CQRS write model, an event-catalog export would fabricate message vocabulary — TODO_LIST.md:68-77) and this audit respects it. But the ruling never considered the other two applicable capabilities: webphone hand-writes a 227-line OpenAPI JSON constant (4 of 23 /api/* paths, schemas unbound from the Go DTOs) and documents its cross-repo wire contracts (ring hook, webhook lanes, SSE kinds) only in Go comments and AGENTS.md prose — consumed by two other repos. A small catalog/openapi + catalog/asyncapi adoption closes both gaps without touching the EventCatalog ruling.

◆Baseline — zero usage, and what's already excellent

Current usage: none. webphone requires three go-cqrs-lite modules directly (metaengine v4.19.0, metaengine/sqliteengine v4.5.3, record v4.6.2 — go.mod:18-20) and carries 21 more indirectly (go.mod:71-91); catalog is absent from the entire module graph. A repo-wide search finds zero references. Adoption cost is unusually low for a new dependency: the spec exporters need only go-error-family (already a direct dep at v0.12.0) plus go-faster/yaml; templ and templ-components are linked only by the docserver package (catalog README.md:24-37).

+
The hand-written spec is disciplined, not sloppy openapiSpec (internal/server/server.go:717-947) is deliberately scoped to "the one machine-facing contract worth publishing", compiles into the binary, and is pinned by three tests (middleware_test.go:196-320) that force every documented response code to match what the handlers actually emit — including the 429 limiter's Retry-After header.
+
The EventCatalog non-adoption is a reasoned ruling Recorded in webphone's TODO_LIST.md:68-77 and the hub's CHANGELOG (2026-10-19): webphone has read models + in-process SSE notifications, no CQRS write model — an event-catalog export would fabricate message vocabulary. pbx-lens is the telephony family's event source. Honest-docs discipline, with a revisit trigger ("only if webphone adopts go-cqrs-lite commands").
+
The wire contracts are typed where it counts The ring-hook payload is a real struct (internal/server/hooks/ring.go:19-23: owner/from/call_id/state), the login DTO fields exist at session_api.go:33-34, and the SSE event names are constants (sse.go:23-24: threads, thread, fax, voicemail, contacts). The gap is publication, not modeling.

01Findings

The 3 applicable capability rows, ordered by impact. All three are missed — nothing is partially used or misused.

Missed Opportunity · High impact

OpenAPI is hand-written as a 227-line JSON constant — catalog generates it from the real Go types

internal/server/server.go:717-947 (const) · :948-953 (handler) · :525 (route) · internal/server/middleware_test.go:196-320 (pins) · catalog README.md:146-292 (REST API documentation)

What the library offers: catalog.Command[T] / catalog.Query[T] with MsgOperation(method, path, codes...), Response[T](code, desc), and SchemaFromType[T]() derive OpenAPI paths from the same structs the handlers decode — field names, required flags, descriptions and formats come from json / doc / format struct tags. Parameters (query/path/header/ cookie) are extracted automatically; Catalog.Validate() detects duplicate operation paths and missing response schemas; DELETE/PUT/PATCH[T] shortcuts cut the boilerplate.

What webphone does instead: a hand-maintained JSON string constant covering 4 paths (/api/session, /api/csrf, /api/contacts, /api/calls) of the 23 /api/* routes that exist — the schemas mirror DTO fields by hand with no compile-time link. The tests pin paths and response codes, but a renamed or restructured field in the session/contacts DTOs would leave the spec's bodies silently stale. Undocumented today: /api/transcribe, /api/transcripts, and /api/push-devices — the last consumed by the new webphone-android shell, which has no spec to build against. 

// Before: hand-mirrored schema inside a 227-line JSON const
// (server.go:729-747 — must be edited in lockstep with the DTO)
"properties": {
  "extension": {"type": "string", "examples": ["1001"]},
  "password":  {"type": "string", "format": "password"}
}

// After: derived from the type the handler actually decodes
b := catalog.NewBuilder("webphone session API", "1.0.0")
b.AddService("webphone", "webphone", "1.0.0",
    "Server session for the tabs and the phone-api proxy",
    catalog.Command[loginRequest]("createSession",
        catalog.MsgOperation("POST", "/api/session",
            "201", "400", "401", "502", "500"),
        catalog.Response[sessionIdentity]("201", "Session created"),
        catalog.MsgSecurity("sessionCookie"),
    ),
    catalog.DELETE[struct{}]("deleteSession", "/api/session"),
    catalog.Query[struct{}]("resumeSession",
        catalog.MsgOperation("GET", "/api/session")),
)
spec, err := openapi.Exporter{}.Export(b.Build()) // schemas from the types
Recommendation Declare the machine API in one registry (start with the current four paths + the three the Android shell consumes), render with openapi.Exporter, serve from the existing /openapi.json route, and keep the three pin tests — they would then pin the generated document. Honest counterweight: for exactly 4 paths a constant is defensible; the trade flips clearly in catalog's favor as the surface grows and schema bodies gain a type binding.
Missed Opportunity · Moderate impact

Cross-repo wire contracts live in comment blocks and prose — AsyncAPI export would give them a machine-readable home

internal/server/hooks/ring.go:19-23 (typed payload) · hooks/webhooks.go:152-169 (contract in a comment) · internal/server/notifier.go:54-71 + sse.go:23-24 (SSE kinds) · AGENTS.md "Gateway seam" / "Push seam" prose · catalog README.md:313-343 (AsyncAPI exporter)

webphone's real async surface spans three repos: the ring hook ({owner, from, call_id, state: ring|end}) is POSTed by the stack's FreeSWITCH dialplan and prunes devices on ErrUnregistered; the webhook lanes (/hooks/message|fax|status|ring) are driven by pbx-artmann's telnyx-webhooks.py bridge; the outbound gateway posts multipart to {url}/message|/fax with a JSON {"provider_ref"} receipt; the SSE stream pushes five named event kinds. Every one of these contracts is documented in Go comments, AGENTS.md prose, or archived plan docs — none in a spec. asyncapi.Exporter{} maps sends/receives/directions to AsyncAPI 3.0 channels from typed messages, and unlike the EventCatalog path this fabricates nothing: these are wire messages that already exist. 

// The ring contract, today: a comment block (webhooks.go:152-161)
//	"owner": the ringing extension
//	"state":    "ring" | "end"

// After: one declared message, exported to docs/contracts/asyncapi.yaml
b.AddService("webphone-hooks", "webphone webhook lane", "1.0.0",
    "Machine lane shared with the pbx-artmann bridge and the FS dialplan",
    catalog.Event[ringRequest]("call.ringing", catalog.Receives),
    catalog.Event[gatewayReceipt]("gateway.receipt", catalog.Sends),
)
Recommendation Follow bank-sync's proven shape (catalog README.md:348-372): a headless webphone -export-contracts subcommand or CI step that writes docs/contracts/asyncapi.yaml from one registry. The pbx-artmann bridge and the Android shell gain a checkable contract; webphone's docs gain a generated one-home instead of three prose homes.
Enabler · Gateway capability

Core registry + schema reflection: the gate to both findings above

not used anywhere · catalog README.md:39-105, 117-143

NewRegistry/NewBuilder, AddService/AddCommand/AddEvent/AddQuery, SchemaFromType[T]() with json/doc/format/ enum tag reflection, and Validate() are the foundation both findings build on. It is scored as a capability row because adopting it has costs of its own that must be planned: the vendorHash re-pin ritual after go get, and a route-vs-registry drift test — Validate() checks internal consistency, not that a declared path has a registered handler (webphone's existing pin tests are exactly the right pattern to extend).
