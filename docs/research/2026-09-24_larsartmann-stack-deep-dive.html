00Summary

Webphone consumes the family deliberately thin: cqrs-htmx root-only (its CQRS core is unused — by documented policy, not neglect), go-cqrs-lite 0% direct (no event sourcing in this product), and go-appkit 0% (not even a dependency). The libraries it does touch are mostly used well: httputil's security headers and rate limiters are fully configured with documented divergences, go-health and cqrs-htmx share one set of check functions with no second readiness truth, and go-sse's test kit pins the SSE wire contract.

Against that baseline the audit found one genuine anti-pattern, one structural under-adoption, and a handful of cheap wins.

The bottom line The fax/message upload route is the only body-unbounded endpoint in the product — ParseMultipartForm(60 MB)'s argument is a memory limit, not a size cap, so an authenticated user can stream an arbitrarily large body to server disk. httputil ships MaxBodySize for exactly this and webphone uses http.MaxBytesReader everywhere else. That's finding #1.

◆What's already excellent

Five KeyedRateLimiter instances with per-surface budgets, and the remoteHostKey XFF divergence has a documented flip rule (server.go:106-120).
+
No second readiness truth /healthz (cqrs-htmx ReadinessHandler + NamedCheck, 2s per-check timeouts) and /startupz + /livez (go-health NewChecks) evaluate the same two check functions — sqlite ping + blob-dir probe (server.go:270-292). The v4.11 NamedCheck.Timeout adoption replaced a hand-rolled boundedCheck: the library beat the workaround, and the workaround was deleted.
+
SSE wire contract is test-pinned with the library's own kit ssetest stream readers + assertions pin the retry-hint head, the connected frame, swap-safe fragment shapes, and payload-less nudge events (internal/server/sse_test.go:114-158). This is the single best test-integration in the repo.
+
Impossible ID confusion, by type Six phantom-branded ID types (ThreadID, MessageID, FaxID…) make cross-entity ID mixing a compile error, with nanoid generation behind id.NewID (internal/domain/ids.go). The Extension/Phone types are hand-rolled — correctly, since they carry format invariants the opaque-ID library doesn't model.
+

Every big "no" has a recorded "why".

01Findings

Ordered by impact. Every card cites the code and the library surface it misses.

Misused · High impact

The upload route is unbounded — ParseMultipartForm's argument is memory, not a cap

internal/server/actions.go:421 · requireSessionMultipart · vs httputil MaxBodySize

r.ParseMultipartForm(uploadLimit) with uploadLimit = 60 << 20 lets the multipart reader buffer up to 60 MB in RAM per request and spill everything beyond that to temp files with no total-size ceiling. Every other write path bounds its body (http.MaxBytesReader: webhooks 40 MB, session/contacts/calls 4 KB) — the fax/message/attachment upload is the one route where a session holder can stream gigabytes to server disk. httputil ships MaxBodySize middleware for exactly this class of problem. 

// Before (actions.go): maxMemory only — total body size uncapped
if err := r.ParseMultipartForm(uploadLimit); err != nil {

// After: bound the stream first, keep maxMemory modest
r.Body = http.MaxBytesReader(w, r.Body, uploadLimit+1<<20) // 61 MB envelope
if err := r.ParseMultipartForm(8 << 20); err != nil {
    http.Error(w, "could not read the form: "+err.Error(), http.StatusBadRequest)
Recommendation Wrap the body with http.MaxBytesReader inside requireSessionMultipart (one line; the existing 400 path already renders the error) or mount httputil.MaxBodySize scoped to the upload routes. Add a smoke/unit probe for an oversize body. Note: not auto-fixed during this audit — another session was mid-edit in internal/server at audit time (166 transient diagnostics); the fix is mechanical and ready above.
Missed Opportunity · High impact (deliberate, but stale)

templ-components: 1 of 121 components used — the Tailwind blocker is documented but never tested

internal/web/views/layout.templ:53 · vs display/forms/feedback/errorpage catalogues

Production usage is exactly layout.Base + PageProps. Meanwhile webphone hand-rolls: avatars with a hue-class CSP workaround (helpers.go:19-71), nav badges as raw spans (layout.templ:137,140), empty states as <p class="wp-empty"> at 9 sites, the 404 + error panel (pages.go:138-152, error.templ) while the library's errorpage module is family-aware with go-error-family integration, and relative timestamps (messages.templ:333-345) vs RelativeTime. The documented blocker — the library emits Tailwind v4 classes while webphone ships unlayered token CSS — is plausible but unproven: unlayered CSS beats layered Tailwind on collisions, so coexistence is likely to just work for isolated components.

Recommendation Run the experiment once: include the library's Tailwind build alongside app.css and render EmptyState, RelativeTime, CountBadge, and errorpage.NotFound404 in a throwaway route. If pixels hold, adopt bottom-up starting with empty states (9 duplicate sites) — each adoption deletes hand-rolled markup AND its test burden. If it fails, the blocker moves from "assumed" to "measured" and the hand-rolls are vindicated.
Missed Opportunity · Medium impact

cqrs-htmx root surface: SafeDetail used once, error text interpolated elsewhere; v4.12.0 adds Retry-After

webhooks.go:28 (only SafeDetail site) · actions.go:422 · pinned v4.11.0, v4.12.0 available

Webphone already reaches for cqrshtmx.SafeDetail to keep internals out of webhook 5xx bodies, but the action handlers still write raw err.Error() into client-visible 400s ("could not read the form: "+err), an inconsistent redaction posture one import away from the library's answer. The root-only policy correctly leaves the CQRS App/dispatch surface unused, but within the root package three things go begging: NotifySuccess/RenderTemplResult (vs hand-built HX-Trigger toast headers — defensible given the morph-swap pattern, worth a line of rationale in AGENTS.md), the BroadcastOn* ACK variants (webphone broadcasts fire-and-forget after store commit), and v4.12.0's Retry-After on 503 — directly relevant to the fail-closed /hooks/* 503s.

Recommendation Route the action-handler error strings through SafeDetail (or the already-aliased pattern) for consistency; queue the v4.12.0 bump for the next train — it also drags the seven indirect go-cqrs-lite modules from v4.10/v4.11.0 to the v4.11.x line cqrs-htmx HEAD wants.
Partially Used · Medium impact

go-error-family: classification adopted, ergonomics hand-rolled

actions.go:308-314 · 5 test files with hand-written family asserts · slog calls with manual "family" fields

The core loop is right: WrapInfrastructuref/WrapTransientf at every boundary, Classified implementations with conditional logic (gateway.ErrProviderRejected maps provider 5xx→Transient, 4xx→Rejection). But three library surfaces are re-implemented by hand: LogErrorContext (webphone writes slog.ErrorContext(..., "family", Classify(err).String()) field-by-field), the errorfamilytest assert family (five test files re-derive it), and Family.Retryable() / Family.HTTPStatus() — the latter deliberately: the pinned two-value contract (Rejection→422, else 502) is a product decision the library's canonical table would change, not express. 

// After: one library call replaces the hand-rolled field packing
errorfamily.LogErrorContext(ctx, logger, err) // family, code, retryable fields, standardized
Recommendation Adopt LogErrorContext + errorfamilytest (cheap, additive); keep the custom HTTP mapping but cite Family.HTTPStatus() in the classifyForUser comment as the rejected alternative, so the next reader knows it was a choice.
Partially Used · Low impact

go-branded-id: SQL Valuer/Scanner unused — the store boundary converts by hand

internal/store/faxes.go:26,45 · internal/domain/ids.go:191-200 · vs id_sql.go

Every store call site stringifies manually (job.ID.String() into SQL params) and the read side prefix-strips via a hand-rolled parseID (strings.Cut + 21-char nanoid check). Verified against the library source: there is no prefix-aware parser to reuse — UnmarshalText takes the raw value — so the hand-roll is currently necessary. But id_sql.go ships sql.Scanner/driver.Valuer (raw-value contract) that would remove the manual conversions entirely — at the cost of changing the at-rest format for new rows (parseID's optional-prefix strip already tolerates both).

Recommendation Optional, low priority: adopt Valuer/Scanner on the next storage-format touch, not as a standalone migration. Keep the Extension/Phone hand-rolls as they are.
Nice to have · Low impact

httputil's httpspec behavioral suite never runs against the webphone chain

no httpspec import anywhere · chain defined at server.go:329-335

httputil ships a 19-spec behavioral suite (httpspec.Run) that asserts security-header, CORS, rate-limit and recorder contracts against a handler. The webphone chain is tested by hand-rolled parity tests (middleware_test.go) that partially re-state what httpspec would check for free on the SecurityHeaders and rate-limiter links.

Nice to have · Low impact

go-health: WithEvaluationHook could feed /metrics; hold v0.4.0 until stable

server.go:284-292 · pinned v0.3.0, v0.4.0 available (alpha)

WithRefreshInterval(0) (live mode) is the right call for two cheap local checks. The unused seam worth remembering: WithEvaluationHook is the library's metrics integration point — the same pattern webphone already uses for CRM lookup counters on /metrics. v0.4.0 is tagged but alpha (WithGETOnly deprecated → WithAllowedMethods) — hold, webphone uses neither option.

Not Applicable · recorded for completeness

go-appkit and go-cqrs-lite: zero usage — with an overlap map for the future

go.mod (no go-appkit require; go-cqrs-lite 100% indirect)

go-appkit is not a webphone dependency. If it ever becomes one, its core module would absorb ~50 lines of hand-rolled main.go (signal handling, drain, /version), realtime would add SSE replay + Last-Event-ID resume (webphone deliberately re-fetches instead), and health adds a dashboard. None of these is a gap today — the hand-rolled versions are small and tested. go-cqrs-lite is fully transitive: the product is not event-sourced by design, so its projections/ metaengine/store modules have no natural entry point. Both verdicts: correct to leave alone; revisit only if webphone grows event-sourced state or a second binary.
