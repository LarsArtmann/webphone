cqrs-htmx — Adoption & Utilization Audit

Does webphone use github.com/larsartmann/cqrs-htmx/v4 — including its auth surface — fully and properly, and does it integrate the library well with the frontend parts? Verdict: the core is adopted correctly and verified by tests; the gaps are periphery, small, and cheap to close.

00Summary

webphone consumes cqrs-htmx root library only — a posture decided on 2026-09-18 and documented in AGENTS.md: middleware + embedded assets + SSE broadcaster + readiness, with the CQRS dispatch layer and the setup/usermgmt/loginpage auth modules deliberately rejected. This audit re-verified that decision against the consumed tag (v4.9.0, not master) and mapped the touched API surface against everything the root module exports. Seven of fifteen applicable capability areas are fully leveraged; four are partially used; three are genuine missed opportunities. The auth rejection is correct and correctly executed: this product's identity is the PBX extension + directory password (proven by the island's SIP REGISTER), and adopting event-sourced usermgmt users would have created a second identity database.

The bottom line Core adoption is exemplary — the middleware chain, embedded HTMX/SSE assets, per-extension SSE hubs, and honest readiness are exactly how the library wants to be used, and each is pinned by a test. The remaining value is periphery: four hand-rolled spots duplicate hardened library helpers (toast wire shape, CSRF header/meta wiring, Server-Timing, 5xx detail redaction), and three embedded capabilities sit unused (request-ID enrichment, the idiomorph extension, a calibrated Permissions-Policy). None is blocking; the top five fixes are each ≤ 20 lines.

◆Current usage — the baseline

Every touchpoint of the library in the codebase, verified by reading the code and the v4.9.0 sources:

+
Middleware chain via Chain RequestLoggingSlog → (optional timing) → SecurityHeaders → RecoveryMiddleware → routes — internal/server/server.go:198-203. Panic path is behavior-tested: 500 to the client, stack in the log, no detail leak (middleware_test.go:40-60).
+
Embedded HTMX 2.0.10 + SSE extension 2.2.4 HTMXScriptHandler() and HTMXExtensionHandler("sse") (server.go:152-153) — same-origin assets with ETag/304, no CDN, CSP-clean. The stack's browser E2E greps survive by construction.
+
Per-extension SSE hubs NewBroadcaster + ServeSSE (subscribe, 15 s heartbeat, unsubscribe) with the canonical Hub().SubscriberCount() reaper and a documented idle-TTL sweep — sse.go:76-118. No deprecated Raw()/NewBroadcasterFromRaw usage.
+
Honest readiness + build metadata ReadinessHandler + NewNamedCheck for /healthz (sqlite ping + blob-dir write probe, 503 names the failing check) and DebugHandler for /version — server.go:165-169, 227-243.
+
Correct posture on deprecated re-exports Security headers, CSRF middleware, and the keyed rate limiter are imported from httputil directly — precisely what cqrs-htmx's deprecation notes on its own aliases instruct (csrf_reexport.go, ratelimit_reexport.go, server_timing_reexport.go at v4.9.0).
+
Deliberate rejections, all documented The setup bundle, usermgmt, loginpage, and casbin AuthorizeMiddleware are unused on purpose (split-brain identity). RecommendedSecurityMiddleware is correctly avoided: its RecommendedPermissionsPolicy denies microphone, which would kill the WebRTC phone.

Architecture of the integration: the server package imports the library for infrastructure (chain, assets, SSE, readiness) while handlers are plain http.HandlerFuncs rendering templ components directly; the island JS never unloads and rides the SSE extension through sse-connect on .wp-root. There is no App, no Command/Query dispatch, and no HTMXMiddleware — by design, the tab URLs separate full pages (/messages) from partials (/partials/messages), so no HX-Request branching is needed.

01Capability assessment

Missed opportunity · High impact, zero risk

Request-ID enrichment unused — logs carry no correlation IDs

internal/server/server.go:198-203 · capability: ContextEnrichmentMiddleware (middleware.go, v4.9.0)

The library ships ContextEnrichmentMiddleware, which generates a RequestID when the client did not send one, sets the X-Request-ID response header, and stamps context so the already-adopted RequestLoggingSlog emits request_id/correlation_id fields (logging.go:224-234, v4.9.0). webphone adopts the logging middleware but nothing ever sets the IDs — so every 3 a.m. log line is uncorrelated with any response. An optional UserIDExtractor would additionally stamp user_id with the signed-in extension.

Recommendation Insert the middleware between the request log and security; the extractor returns the session's extension (zero error for anonymous requests — the middleware skips them). 
// server.go New():
return cqrshtmx.Chain(
    cqrshtmx.RequestLoggingSlog(slog.Default()),
    cqrshtmx.ContextEnrichmentMiddleware(extensionExtractor), // NEW
    timingMiddleware,
    security,
    cqrshtmx.RecoveryMiddleware,
)(root)

// extensionExtractor reads the session cookie and reports the
// extension as the user id: func(r *http.Request) (cqrshtmx.UserID, error)
Anti-pattern shape (latent) · partially used

Frontend CSRF wiring hand-rolled where hardened helpers exist

internal/web/views/layout.templ:136,147 · capability: httputil.CSRFTokenHXHeaders / CSRFTokenHTMLMeta / InvalidateCSRFCookie (csrf.go:902-935, 483)

The hx-headers attribute is built by string concatenation: `{"X-CSRF-Token":"` + props.CSRFToken + `"}`. httputil.CSRFTokenHXHeaders exists precisely because that shape is an XSS sink whenever the token is not the middleware's hex token — its own doc comment says so, and it HTML-escapes the JSON for the attribute context (csrf.go:920-923). Today the token is nosurf base64url, so nothing is exploitable — but the construction is one refactor away from the documented footgun, and the same-family helpers are already one import away. Additionally, InvalidateCSRFCookie (rotate-on-login to prevent CSRF fixation) is never called on POST /api/session or logout. The auth-integration verdict: CSRF is integrated correctly end-to-end (middleware → meta → hx-headers → island fetch headers) — it just does not use the library's hardened builders.

Recommendation Build the attribute from the helper in renderShell, keep the templ-escaped <meta>, and rotate the CSRF cookie on session create/destroy. 
// pages.go renderShell — before:
props.CSRFToken = csrfToken(r)

// after:
props.CSRFToken = httputil.CSRFTokenFromRequest(r)
props.CSRFHxHeaders = httputil.CSRFTokenHXHeaders(r)

// layout.templ bodyAttrs — before:
"hx-headers": `{"X-CSRF-Token":"` + props.CSRFToken + `"}`,
// after (safe by construction):
"hx-headers": props.CSRFHxHeaders,

// session_api.go createSession — after SetCookie:
httputil.InvalidateCSRFCookie(w, httputil.CSRFConfig{})
Missed opportunity · medium impact, needs E2E validation

Embedded idiomorph extension unserved — SSE swaps wipe composer drafts

server.go:152-153 (only "sse" served) · capability: HTMXExtIdiomorph, idiomorph 0.7.4 (htmx_extensions.go, v4.9.0)

cqrs-htmx embeds the idiomorph extension alongside SSE (cqrshtmx.HTMXExtIdiomorph, version 0.7.4), but webphone serves only sse.js. The fragment design was explicitly shaped by the constraint that sse-swap replaces innerHTML — "a wrapped payload would nest panels and wipe drafts" (AGENTS.md). Morph-based swapping preserves unmodified DOM (input focus, composer drafts) across panel updates, which is the same class of problem. Adoption must keep the browser E2E green and the DOM contract intact, so treat this as a measured experiment, not a drop-in.

Recommendation Serve it (one line), then evaluate hx-ext="morph" with sse-swap="morph" on the transcript panel only; re-run the stack's browser E2E before keeping it. 
// server.go — one line:
open.Handle("/htmx-ext/idiomorph.js",
    cqrshtmx.HTMXExtensionHandler(cqrshtmx.HTMXExtIdiomorph))
Partially used · hand-rolled duplicate

40-line timing writer duplicates servertiming.ServerTimingMiddlewareWhen

internal/server/server.go:245-287 (timingWriter + timingMiddleware) · capability: server_timing v1.0.1 (already an indirect dependency)

The env-gated Server-Timing: total;dur middleware is hand-rolled — custom writer, implicit-200 handling, Flush forwarding, Unwrap. The library's ServerTimingMiddlewareWhen(pred) does all of that and more: it auto-prepends total;dur ("Total request", server_timing.go:341), sanitizes values against CRLF injection, delegates Flush/Hijack/Push (SSE-safe), and passes through with zero overhead when the predicate is false — exactly webphone's WEBPHONE_DEBUG_TIMING gating. Swapping deletes ~40 lines and adds named-span support for free (MeasureServerTiming around PBX calls).

Recommendation Replace both symbols with the library middleware at the same chain position (just inside the request log, so the measured span stays the whole route stack). 
// server.go — before: timingMiddleware + timingWriter (~40 lines)
// after (3 lines, same position in the chain):
servertiming.ServerTimingMiddlewareWhen(
    func(*http.Request) bool {
        return os.Getenv("WEBPHONE_DEBUG_TIMING") != ""
    },
)
Partially used · wire-shape drift risk

toastDetail re-declares cqrshtmx.ToastDetail instead of aliasing it

internal/server/toast.go:12-15 · capability: ToastDetail (notify.go:10, v4.9.0) — root package, not dispatch-layer

The local struct's comment justifies itself as avoiding "dispatch-layer types" — but ToastDetail lives in the root package webphone already imports, and the server package depends on cqrs-htmx anyway (server.go:19). Both library UI modules (adminui, dashboardui) alias it (type toastDetail = cqrshtmx.ToastDetail) so the {message, kind} wire shape cannot drift from the island's showMessage listener. Worth one caveat to document while touching this: the dispatch-layer Notify* options emit a different shape ({level, message}, notify.go:89-93) — if the dispatch layer were ever adopted, toasts would silently stop matching the island listener.

Recommendation Two-line change; the island listener comment already names the library type. 
// toast.go — before:
type toastDetail struct {
    Message string `json:"message"`
    Kind    string `json:"kind"`
}
// after:
type toastDetail = cqrshtmx.ToastDetail
Missed opportunity · cheap hardening

Permissions-Policy header absent — the calibrated version is one config field away

internal/server/server.go:187-192 (SecurityHeadersConfig) · capability: PermissionsPolicy field (httputil security.go:56) and RecommendedPermissionsPolicy (v4.9.0)

SecurityHeadersConfig.PermissionsPolicy is left empty, so the browser's default allow-posture applies to camera, geolocation, payment, usb, and microphone. The library's RecommendedPermissionsPolicy must stay rejected (it denies microphone and would kill the phone) — but the deliberate rejection of the wholesale preset has left the calibrated policy unshipped. Denying everything except self-originated microphone is strictly more hardening than absence, on the one surface (the login page) that needs nothing at all.

Recommendation One field in the existing config literal; the island needs microphone=(self) and nothing else. 
security := httputil.SecurityHeaders(httputil.SecurityHeadersConfig{
    ContentTypeNosniff: true,
    // ...existing fields...
    PermissionsPolicy: "microphone=(self), camera=(), geolocation=(), payment=(), usb=()",
})
Partially used · 5xx detail redaction

Webhook error bodies interpolate err.Error() into 500 responses

internal/server/webhooks.go:127,202,243,282 · capability: SafeDetail / MapError / error-family classification (errors.go, v4.9.0)

Provider-facing 500 bodies include raw error strings ("could not store message: "+err.Error()). The library's error model exists to prevent exactly this: SafeDetail(err, status, includeInternal) redacts 5xx detail, and MapError resolves statuses from error families so transient store failures answer 503 (retryable) rather than 500. The paths are secret-gated, so exposure is bounded — but the bodies also feed the provider's retry logic, where a 503-vs-500 distinction has behavioral meaning.

Recommendation Keep the operator-plain style, but route the final string through cqrshtmx.SafeDetail(err, http.StatusInternalServerError, false) and classify store failures as 503.

05Conclusion

Yes — webphone uses cqrs-htmx properly: the root-only posture is deliberate, documented, and matches what the library is for at this product's identity model, and the auth modules were rejected for the right reason with the right replacement (PBX-proven sessions + httputil CSRF). Integration with the frontend parts is tight where it matters — embedded assets, SSE-driven partials, CSRF reaching both HTMX and the island's fetch calls, and every adoption pinned by a test. The 22-point distance from 100 is periphery: five small adoptions of helpers that already sit one import away, one latent anti-pattern shape to retire, and one measured experiment (idiomorph) that could remove the draft-wipe constraint that shaped the whole fragment design. Doing the top five would take an afternoon and lift the score to the mid-90s.
