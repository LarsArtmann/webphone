00Summary

webphone pins github.com/larsartmann/templ-components and imports exactly one symbol: layout.Base in internal/web/views/layout.templ. Every other surface is a deliberate hand-roll on top of a custom, freshly redesigned token CSS (app.css, 1219 lines) with a strict zero-inline-script CSP. The library emits Tailwind v4 classes; webphone loads no Tailwind CSS at all — which is why the catalogue is dead weight today, not negligence.

The bottom line The best leverage was not adopting more components — it was fixing the one adoption that hurt. Base's forced inline dark-mode script forced webphone to hash-pin dependency bytes in its CSP. This audit shipped PageProps.NoThemeScript upstream (v1.19.2), bumped the consumer, and deleted the hash pin plus the !important color-scheme hacks: a dependency bump can now never change served script bytes.

◆What's already right

+
Base is used with its suppression idioms, not fought CSSPath and HTMXVersion are zeroed in props (layout.templ:53-64) so the page embeds only same-origin assets; SEO carries NoIndex; ThemeColor/DarkThemeColor are set for both schemes.
+
The hand-rolls are deliberate, documented decisions Avatars (avatarFor/avatarHue with tests — the CSP-safe hue-class workaround), timestamps (formatClock/formatStamp byte-stable for the stack E2E), nav badges, empty states, and the brand SVG each own a reason; the library's image-based Avatar or RelativeTime would regress pinned behavior.
+
Icons-only adoption was evaluated and honestly rejected The icons package is CSS-agnostic (docs/icons-only-adoption.md) and would have been the easy win — but webphone's views contain exactly one hand-rolled SVG: the brand mark, which is custom artwork and should stay.
+
Zero-inline-script CSP is now structural, not pinned TestServedPageSatisfiesStrictCSP fails on ANY inline script and on any hash/unsafe-inline in script-src (server_test.go) — the strongest possible posture for a consumer that embeds a third-party UI library.

01Findings — ordered by impact

Misused · EXECUTED this cycle

Base's forced inline theme script forced a CSP hash pin on dependency bytes

internal/server/server.go (contentSecurityPolicy) · layout.templ headExtras · upstream layout/base.templ:252

Base emitted its dark-mode preload <script> unconditionally (no opt-out through v1.19.1). webphone — whose CSP allows no inline scripts — had to pin the exact script hash and fight the script's inline colorScheme write with !important CSS. Every dependency bump risked a broken page until the hash was re-pinned by hand (documented as a standing watch since 2026-09-18). The library's own doc notes the script is only needed for the toggle dark strategy — webphone themes via data-theme, making the emitted bytes 100% inert. 

// Before (v1.18.0): hash-pin the dependency's script bytes
"script-src 'self' 'sha256-AO4OqWm6...'; ..."
:root[data-theme="light"] { color-scheme: light !important; }

// After (v1.19.2 + this repo): same-origin file, zero inline scripts
// layout.templ
NoThemeScript: true,
HeadContent:   headExtras(props.CSRFToken)  // <script src="/assets/theme-preload.js">

// server.go
"script-src 'self'; ..."
Executed Shipped upstream as PageProps.NoThemeScript (templ-components v1.19.2, pinned by TestBaseThemeScriptSuppression); webphone consumes it and serves its own render-blocking /assets/theme-preload.js, which also fixes a real gap — the old script never set data-theme, so forced-theme FOUC prevention now actually works pre-paint.
Partially Used · EXECUTED this cycle

Two minor versions of upstream fixes unclaimed (v1.18.0 → v1.19.2)

go.mod:19 · upstream CHANGELOG v1.19.0/v1.19.1/v1.19.2

The gap carried a real popover-positioner fix (panels rendering at (0,0) — the toggle event does not bubble; capture-phase listener + self-healing attach), DropdownProps.Trigger, the ListNote count-only variant, NoMainWrapper (double-<main> a11y fix the website needed), and hybrid strings.Builder rendering docs. None bit webphone today because only Base is consumed — but any future adoption would have inherited stale bugs.

Executed Bumped to v1.19.2 in the same change as the knob consumption; the CSP-hash test class that made bumps scary is gone (see finding 1), so future bumps are ordinary dependency work.
Missed Opportunity · OPEN, strategic

No compiled Tailwind layer — 120 of 121 components are structurally unusable

internal/web/assets/assets.go (embed list has no Tailwind output) · app.css:107 ("this app does not load Tailwind")

Every component emits Tailwind v4 utility classes; without a compiled stylesheet they render unstyled. webphone's fresh token system (app.css) was a deliberate 2026-09-20 redesign, so wholesale adoption is anti-value today — but the coexistence path is real and unproven: Tailwind v4 emits cascade layers, and unlayered app.css rules win collisions regardless of load order. A scoped build (@source the module cache + views, @theme aliasing webphone tokens) would make one-component experiments a one-import change. Two stale consumer comments claiming a "Tailwind build" exists were fixed during this audit (assets.go, layout.templ) — the docs lied about the pipeline in both directions. 

/* future assets/tw.css — scoped to the library, themed to webphone */
@import "tailwindcss" layer(tc);
@source "$(go env GOMODCACHE)/github.com/larsartmann/templ-components@v1.19.2";
@theme {
  --color-teal-600: var(--accent);        /* alias webphone tokens */
  --color-gray-900: var(--text);
}
Recommendation Prove coexistence with exactly ONE low-risk component (e.g. feedback.InlineLoading in a tab partial) behind the layered build; measure visual diffs against app.css. If clean, the errorpage family (next finding) becomes adoptable.
Nice to have · OPEN, blocked on Tailwind decision

errorpage family could replace the hand-rolled ErrorPanel

internal/web/views/error.templ (ErrorPanel) · library errorpage/ module (ErrorPage, NotFound404, ErrorDetail, WriteError)

webphone's ErrorPanel is 13 lines doing the right things (what/reassurance/reload, i18n'd, styled 404 with shell). The library's errorpage module adds go-error-family awareness, WCAG-hardened focus order, HTML-validator-clean markup, and trace footers — but emits Tailwind classes, so adoption is gated on finding 3. Not worth churn while the current panel is tested and green (TestNotFoundRendersTheShell).

Not Applicable · verified deliberately

Most of the catalogue should stay unadopted

helpers.go (avatars, clocks) · layout.templ NavLinks · voicemail/fax/contacts/history .templ empty states

Checked against the catalogue and rejected on evidence: display.Avatar (image-based; webphone's is a tested initials+hue system), display.RelativeTime (client-relative text would churn byte-stable pins), navigation.Pagination (thread paging is a shell.js state machine, not URL pagination), htmx.GlobalErrorHandling (shell.js §3c already implements the toast pipeline with island-owned throttling), feedback.Toast (would split-brain the island's toast live region), icons (one custom SVG total). Per the audit rules: 121 features where ~8 are relevant and 1 is optimally used is a posture, not a failure — the UI is the product here and it was redesigned on purpose three days ago.
