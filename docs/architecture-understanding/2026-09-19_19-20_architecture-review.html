00Summary

webphone is a deliberately small, sharply layered single binary: a pure domain, services that never import HTTP, one static composition root, and two real seams (carrier gateways and change notification). Dependency direction is not a convention here — it is enforced by internal/arch/arch_test.go, which ran green during this review. The structural scores below extend the 18:49 DI/health review in this directory with the sweep's findings; nothing found today lowers them.

Verdict Properly service-oriented and composable for its scale; the two open items (liveness story, sanitizer alignment) are decisions, not structural defects.

◆What's already excellent

+
Executable dependency directiondomain imports nothing internal; services never import server/web; island module graph stays acyclic. Breaking the layering fails go test, not a code review.
+
Seams only where variability is realMessageGateway/FaxGateway (two implementations, config-picked; loopback runs the whole product with zero externals) and ChangeFunc (observer without imports). Stores stay concrete on purpose.
+
The island-never-unloads decisionTab navigation swaps HTMX partials while the SIP island lives outside the swapped region — calls survive navigation by construction, and the arch test keeps the JS module graph consistent with it.
+
Contract tests as the module boundary with dependenciesCSP hash parity, DOM ids, CSRF JSON shape, HX-Trigger toast alias: upstream drift fails this build instead of surfacing in a browser at the customer's desk.
+
Deployment shape ships with the binarynixosModules.default keeps the systemd hardening, the CSRF fronting defaults and the vhost contract in the same repo as the code that needs them, with a flake check asserting the rendered shape.

03Should this be split into Go modules? No.

The modularize decision table scores three High signals against splitting: ~13 packages (small project), no external package consumers (the flake input consumes the built binary, not Go packages), and everything co-changes through the single product surface. The internal/ tree already gives compile-time opacity; a second go.mod would add version ceremony with zero composability payoff. Revisit only if a second consumer starts importing internal/domain or internal/gateway directly.
