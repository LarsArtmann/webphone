00The constraint that makes this hurt

Facts verified at HEAD 94cf4365:

  • internal/messaging/service.go:255-371 holds ten read methods whose bodies are 1–3 lines each — pure forwards into the readmodels.ThreadGate plus a readmodels.SummariesOfView conversion (ResolveThread, Threads, AllThreads, ThreadAny, ArchivedThreads, ArchivedCount, ThreadSearch, Thread, ThreadWindow, MarkRead; AttachmentByID/Any at :437-446 are the same shape).
  • server.Deps carries BOTH routes: Messages readmodels.ThreadGate (server.go:206) and Messaging *messaging.Service (server.go:255). The paths already diverged — platform reads the gate directly (platform/export.go:84,121; platform/metrics.go:42,47) while the html surfaces ride the forwarders (panels.go:53-110, actions.go:433,573,626, admin.go:120,129,251 — thirteen sites).
  • A third conversion site exists: the Notifier renders list pushes through ListThreads + SummariesOfView (notifier.go:110-111).
  • No test pins the forwarders: messaging's suites cover Send/Receive/senders/selfsend/blob-rollback/race — none cover the reads. Deletion test passes: deleting the forwarders deletes complexity; it does not reappear (handlers already know the gate's nouns — panels.go builds crmNumbers(threads …) over readmodels.ThreadSummary today).
The hurt every new thread reader must choose between two paths, and the choice has already split; the choice is invisible to the depth budget (messaging is 486 LOC, under every ceiling) so nothing gates it — only a real seam decision fixes it.

03The deepened shape (design B)

// readmodels — the gate after the fold (reads only shown)
type ThreadGate interface {
    // summary reads — ThreadSummary, render-ready, owner-scoped
    ListThreads(ctx, owner) ([]ThreadSummary, error)
    ListArchivedThreads(ctx, owner) ([]ThreadSummary, error)
    SearchThreads(ctx, owner, needle) ([]ThreadSummary, error)
    ListAllThreads(ctx, limit) ([]ThreadSummary, error)   // admin-gated by reachability

    ThreadWindow(ctx, owner, id, page) (Thread, []Message, bool, error)
    GetThread / GetThreadAny / MarkThreadRead / SetThreadFlag …  // unchanged
    // deleted from the interface: ListMessagesPage (single caller was the forwarder)
}

What the interface promises callers: owner scoping on every read (the gate enforces it, handlers stop re-deriving it); absent = store.ErrNotFound sentinel, unchanged; lists are render-ready summaries; the window read pages newest-first with an honest hasMore. What stays outside the seam: CRM enrichment (crmDirectory/crmNumbers at the handlers), the unread hub, props assembly, the Notifier's event→push policy table (machine-tables ruling), and every write path — the pipeline module keeps them.

Which tests survive: all of them, minus nothing — messaging's suites never covered reads; server handler tests go through the same compositions unchanged (byte-pinned panel tests included); notifier tests unchanged. New pin: extend cqrs/threadspaging_test.go to pin ThreadWindow's page-0 and hasMore semantics at the gate, since the composition moves inside.
