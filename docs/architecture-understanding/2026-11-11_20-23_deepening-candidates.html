1 · Deepen the thread list read model

Strong in-process

Before — the shape lives in three modules

bridge: SummaryOfView re-parses view → store shape
readmodels ThreadSummaryView (engine wire)

After — one deep module owns the shape
readmodels — thread list module
ThreadSummary · ThreadFlag (moved)
gate: ListThreads · Thread · SetFlag · MarkRead

Problem: the render shape's interface lives beside retired SQL rows, and ThreadFlag is defined twice (store + readmodels) — a field change touches 3 modules of implementation and 4 of consumers.

Solution: ThreadSummary and ThreadFlag move into readmodels; the gate is the one seam every consumer already speaks.

  • locality: field changes concentrate in one module
  • bridge module deleted (deletion test passes)
  • store shrinks toward its sessions-only end state
  • leverage: one interface, N consumers
Aligns with the storage-ladder freeze ruling — no ADR conflict.

4 · One adapter owns push delivery policy

Strong ports & adapters
internal/push/push.go · internal/server/hooks/ring.go · internal/server/api/summary_api.go · internal/fax (draft fan-out caller)
sequenceDiagram
  participant R as ring hook
  participant F as Fanout (deep)
  participant N as ntfy / FCM adapters
  Note over R,N: Before — policy re-implemented per caller
  R->>R: send loop, request context, blocks the 202
  R->>N: send × devices (synchronous)

Problem: "fire a push without blocking, prune the dead" is implemented twice, divergently — and Fanout's own interface is as wide as its implementation (Send/SendDraft duplicate the guard+route boilerplate); the prune needs the device registry, which is why callers compose the loop themselves.

Solution: a deep Fanout.FanEvent(ctx, owner, event) owns detach + budget + prune-on-unregistered; both caller loops die (deletion test passes), callers hand facts.

  • the ring contract violation fixes itself
  • leverage: one policy, three callers
  • two adapters already exist — real seam
  • prune logic stops living in a hook
