## e) WHAT WE SHOULD IMPROVE (process, not code)

1. **Never act on a staleness/drift verdict from scoped runs** — the
   verified rule is now in `.buildflow.yml`, but the general principle
   (a verifier scoped to tool A cannot adjudicate tool B's accepted-noise)
   deserves a line in docs/lessons.md.
2. **Read the existing pins BEFORE concluding type semantics** —
   `ids_test.go` encoded the prefix contract the whole time. "Search the
   tests for the fact" is cheaper and more reliable than "derive from
   library source".
3. **Directive placement convention needs one canonical statement** — the
   working form is: `//cqrs-lint:ignore(RULE)` as the FIRST comment on the
   finding's line OR on the immediately-preceding line (blank lines are
   skipped, comma-lists supported by current CLI, comma-lists SUSPECT under
   the stale BuildFlow embed). One AGENTS.md sentence would spare the next
   session my three iterations.
4. **The `/*`-in-comments hazard is a repo-wide landmine** — any future
   `image/*`-style prose silently kills every cqrs-lint directive below it
   in that file, with NO diagnostic (the scanner just goes quiet). The
   upstream fix is the real cure; until then the pattern deserves a lesson.
5. **Scoped-run hygiene**: when a scoped buildflow step disagrees with the
   underlying tool's own CLI, the CLI wins — worth a standing rule.
6. **Config-disable vs keep-visible vs directive needs a decision table** —
   I applied: config-disable = permanent architecture; directive = per-site
   fact; keep-visible = must stay armed. Writing that table down (one home)
   would make the next triage mechanical.
