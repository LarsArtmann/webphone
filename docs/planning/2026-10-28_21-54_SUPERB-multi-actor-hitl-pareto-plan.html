0. Problem

The product asks: how do we work with multiple users and multiple AI agents, with the user fully or partially in the loop? Verified at HEAD, the autonomy machinery is further along than the backlog admits: the supervised textagent seam ships approve/discard with human edits, confidence-gated autopilot, a kill switch (frozen conversations), STOP suppression, runtime mode pinning, missed-call and automatic post-call draft initiation, push-notified approvals, and persisted review artifacts (domain.ReviewState pending/present/failed). What is missing is the actor model underneath and one rung of the autonomy ladder:

  • The webphone session row carries extension + password only — the login email is verified, logged, then discarded at mint. Two humans sharing an extension are indistinguishable in agentAudit, the API lane, and every future delegation/quorum decision. This is the 1% that blocks 51%.
  • authmap.User.Extensions already models N extensions per human, but SessionExtension() pins to the first — a multi-line operator cannot switch lines.
  • MappedByExtension iterates a Go map — on a shared extension the whoami identity is randomly chosen per boot.
  • The drafts panel shows language · confidence but not pending age — the one signal that makes a veto-window or staleness policy legible.
  • The ladder’s middle rung — time-boxed escalation (auto-send after T unless a human vetoes) — does not exist anywhere; agent-side (stack/textagent) work.
  • There is exactly ONE machine actor (the textagent, bearer-secret). A second agent has no identity, no lane, no per-agent audit.

The rails that make L2/L3 safe: audit with actor identity (this train), pending-age visibility (this train), push nudges (shipped), kill switch + STOP (shipped). The ladder is per-deployment and per-mode — never a global constant.

2. The actor model (the design answer)

  • Human actors are emails resolved through ONE mapping (authmap), regardless of login mode (passkey or OIDC). A session remembers WHO minted it (LoginEmail, empty = classic extension login). Every action line names its actor: email when known, extension otherwise.
  • Machine actors are named agents with scoped credentials. Today: the textagent (bearer secret, loopback). The design target: a registry where each agent has a name, a scope (draft? read? send?), and audit lines prefixed by its identity — the same rule the humans follow.
  • Delegation (future, owner call): a human grants another human or an agent a scoped approval right (per-contact, per-window). Requires the actor substrate first — you cannot delegate a right you cannot attribute.
  • One audit home per actor class: authAudit (identity events), agentAudit (agent-action events) — both carry actor identity after this train; the durable read model stays deferred (F107) with a sharpened trigger.

7. Verification doctrine (anti-verschlimmbessern)

  • Byte-parity for extension logins: empty LoginEmail must leave every wire shape, audit line class, and DB behavior identical to today (the omitempty doctrine).
  • One birth path: mintSession stays the only session-mint home; the email rides the existing Create call, no second variant.
  • Migration honesty: the sessions table is owned by the session seam (not the store/db.go ladder); the guarded ALTER is the column-level equivalent of its established IF NOT EXISTS pattern, idempotent and re-run-safe.
  • Gates: train-start AND train-end buildflow (daemon-truncation doctrine); nix fmt before gates (treefmt owns templ-adjacent + Go alignment); templ generate after any .templ edit; session-behavior suite for auth-adjacent changes (auth: prefix on the commit).
  • No autonomy shipped silently: nothing tonight changes what the agent may send. L2 stays a spec until the owner rules.
