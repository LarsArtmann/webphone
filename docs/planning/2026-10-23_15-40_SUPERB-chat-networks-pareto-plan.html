Signal · Session · Matrix

Today every conversation is implicitly telephony: threads key on (owner, remote phone), the outbound seam is the SMS/MMS gateway, and inbound arrives on Telnyx webhooks. Supporting chat networks means generalizing exactly three things — the identity of the far end (a Signal number, a Matrix room, a Session ID are not phone numbers), the outbound seam (one sender per network), and the inbound seam (push receivers, not just webhooks). Everything else — threading, delivery lifecycle, flags, search, SSE, attachments, UI — already generalizes for free.

The 20% that carries 80%: a typed domain.Network (sms | signal | session | matrix) plus a typed domain.Address (network-validated remote), threaded through the store, the messaging service, and the views. Once a thread knows its network, every sender is just another gateway.MessageGateway implementation and every receiver just another caller of messaging.Service.Receive.

01Research (verified at source)

Signal — signal-cli is the integration path

Verified against AsamK/signal-cli v0.14.9 docs + man pages, nixpkgs pkgs/by-name/si/signal-cli. The daemon (signal-cli daemon --socket) speaks JSON-RPC 2.0 on a unix socket: send accepts {"recipient":["+49…"],"message":"…","attachments":["data:<mime>;filename=…;base64,…"]} and answers with the send timestamp (our correlation ref). Incoming messages are pushed as JSON-RPC notifications with method receive, carrying envelope.source, dataMessage (body, attachments with contentType/filename), and receiptMessage (isDelivery / isRead + acknowledged timestamps) — the full delivery-receipt story maps onto our existing DeliveryReceipt seam. Accounts link via QR (startLink/finishLink over the same socket). Packaged in nixpkgs at 0.14.9 (GPL-3, JVM). Caveats: linked devices must stay <3 months stale; inbound attachments stay in signal-cli’s data dir in v1 (skipped with a WARN, documented).

Matrix — plain Client-Server API, no SDK needed

Verified against spec.matrix.org v1.19. Sending is one PUT: PUT /_matrix/client/v3/rooms/{roomId}/send/m.room.message/{txnId} with Authorization: Bearer …, body {"msgtype":"m.text","body":"…"}, answering {"event_id":"$…"}; the txn id makes retries idempotent. Receiving is the long-poll GET /sync?since=…&timeout=30000; DMs are identifiable via global m.direct account data; media is POST /_matrix/media/v3/upload → mxc:// and the v1 media download endpoint. A long-lived access token minted once by POST /login is the standard bot pattern. Encrypted rooms (m.room.encrypted) are legally skippable by a non-E2EE client — we restrict to plaintext rooms and say so in Settings.

Session — researched, and the honest answer is “not yet”

Verified across oxen-io / session-foundation orgs. There is no Go library (the only Go repo in the foundation org is a CI config), no official bot API, no headless daemon. The blessed libsession-util (C++, foundation-maintained) covers config/crypto, but swarm polling, onion-request construction, namespace signing and protobuf envelopes live inside the client apps. The realistic options are a single-maintainer community SDK (session.js, Bun, MIT, bus-factor 1, last commit 2026-01) or writing a Session client from scratch. Both fail this repo’s durability bar for a security-sensitive seam.

02The Seam Design

Data model first: the network axis

Mandatory reflection, in order: What is it in the domain? A network is the messaging transport + identity system a conversation rides (telephony SMS, Signal, Matrix…). Lifecycle? Immutable at thread birth — conversations never migrate networks; every message inherits its thread’s network. Invariants? A thread has exactly one network; the remote address validates against that network’s rule; the outbound route is a pure function of the network. Independent axes? Network (transport) is orthogonal to channel (format: sms | mms — that type keeps its meaning untouched) and to the pin/archive/mute flags. Painful later? The unique key — hence migration v5 rebuilds UNIQUE(owner, remote) as UNIQUE(owner, network, remote). 

type Network string // "sms" | "signal" | "session" | "matrix"

type Address struct {
    network Network // owns the validation rule
    value   string  // E.164-ish | @mxid:host | 05… session id
}

ParseAddress(network Network, raw string) (Address, error) // THE door

domain.Phone survives untouched for the lanes where a phone really is the concept: fax, contacts, dial affordances, CRM enrichment, history. Only the conversations model generalizes. ParseAddress(sms, …) reuses the exact sanitizeDialable rule — zero behavior change for existing rows.

Outbound: a sender per network

gateway.MessageGateway already is the right interface; OutboundMessage.To generalizes from Phone to Address. The messaging service keeps a map[Network]MessageGateway: the telephony gateway registers under sms (exactly as today — New() signatures stay compatible), matrix/signal clients register behind their config gates. An unregistered network is a Rejection with an honest operator-facing reason, never a silent drop.

Inbound: receivers reuse the webhook pipeline

Matrix’s /sync loop and signal-cli’s socket reader are background consumers that call the very same messaging.Service.Receive the webhook lane calls — persistence, AppendToThread auto-unarchive, unread counting and SSE notification are inherited wholesale. Matrix persists its next_batch cursor in the existing app_flags table (one home, no new machinery). Both receivers reconnect with backoff; both are lifecycle-bound to the composition root’s context.

UI contract

Thread rows and heads grow a network badge (English label, no new pinned DOM ids); data-dial renders only for SMS threads; the reply composer posts to the thread it already targets — the server derives the address from the thread row, never from client-supplied strings; new-conversation compose stays SMS-only in v1 (chat threads are born from inbound). The event log stays English; i18n keys land in both maps per house rule.

03Decision Log

D1 — Matrix: hand-rolled thin client, mautrix-go REJECTED. The repo already hand-rolls its HTTP seams (pbx.Client, crm.Client, asr.Client). mautrix-go drags in the full E2EE state machinery and a large dependency tree for capability we deliberately do not want (plaintext rooms only); the CS-API surface we need is three endpoints. VendorHash cost, attack surface, and the 20-year-durability posture all favor ~300 stdlib lines we own.
D2 — Signal: raw signal-cli unix socket, signal-cli-rest-api REJECTED. The REST wrapper is an extra JVM container hop whose receive endpoints have no authentication, and its webhook mode is a lossy re-encoding of the same JSON-RPC notifications we can read directly. The unix socket is local-only by filesystem permissions — the same trust boundary as the loopback gateway.
D3 — Session: NO-GO now. Reopen triggers: (a) an official or foundation-blessed headless daemon/bot API appears; (b) a maintained Go implementation of the Session protocol emerges; (c) the owner accepts a session.js sidecar (Bun, single-maintainer, MIT) knowing it is research-grade — then it becomes a stack-side service question first.
D4 — Scope fences for v1. Matrix: DM rooms, plaintext only, media both ways; group rooms and read-receipts follow. Signal: 1:1 DMs, text outbound + data-URI attachments, delivery receipts wired; groups and inbound attachments follow (they need signal-cli-side plumbing). Both: OFF by default, byte-identical product at zero config — the passkey/ASR/CRM gate pattern.

06Risks & Standing Limits

  • Migration v5 rebuilds the threads table (SQLite cannot drop an inline UNIQUE). Threads are small (per-extension conversations); the rebuild runs once, versioned, transactional.
  • Matrix E2EE: encrypted rooms are skipped — surfaced in Settings, never silent.
  • signal-cli is a JVM sidecar — deployment (stack repo: systemd unit, linked-device QR ritual, 3-month freshness) is follow-up work in nix-international-telephony; webphone ships the client now, config-gated OFF.
  • Served-markup changes owe the stack browser E2E (standing rule) — rides the next relock.
  • CRM enrichment is number-keyed by design — chat-network threads render verbatim identities; the CRM miss is graceful (documented, not “fixed”).
  • Rate limits: matrix client honors Retry-After/429; signal send surfaces retryAfterSeconds as a transient failure.

07Definition of Done

  • Zero config ⇒ byte-identical product (render-diff discipline + the parity tests).
  • With matrix.* set: a DM on a real homeserver appears as a thread; replies send; media flows; encrypted rooms skipped loudly.
  • With signal.* set against a live signal-cli socket: DMs both ways; delivery receipts flip the status badge live.
  • Full gate suite green: go tests, island specs, nix fmt, buildflow; CHANGELOG/TODO/AGENTS updated; plan verdicts recorded.
